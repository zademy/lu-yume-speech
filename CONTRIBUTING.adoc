= Contributing to LU YUME — Speech-to-Text
:toc: left
:toclevels: 3

Thank you for your interest in contributing! This guide covers everything you need to set up the project, make changes, and submit them for review.

== Quick Start

=== Prerequisites

* **Node.js** >= 20
* **pnpm** >= 9 (install via `npm install -g pnpm` or https://nodejs.org/api/corepack.html[corepack])
* **Rust** stable (install via https://rustup.rs[rustup]) — required for desktop builds
* https://tauri.app/start/prerequisites/[Tauri system dependencies] for your OS
* A **Groq API key** from https://console.groq.com[console.groq.com]

=== Setup

[source,bash]
----
# Clone your fork
git clone https://github.com/<your-username>/speech-to-text.git
cd speech-to-text

# Install dependencies
pnpm install

# Start desktop development shell (recommended)
pnpm tauri dev

# OR start web-only dev server (fallback)
pnpm dev
----

The desktop shell opens in a native window. The web-only server is at http://localhost:5173.

== Development Workflow

=== Branch Naming

Use descriptive branch names with a prefix:

|===
| Prefix | Purpose | Example

| `feat/` | New feature | `feat/silence-threshold-slider`
| `fix/` | Bug fix | `fix/waveform-render-crash`
| `docs/` | Documentation | `docs/add-api-reference`
| `refactor/` | Code restructuring | `refactor/extract-audio-module`
| `chore/` | Tooling / maintenance | `chore/upgrade-vite`
|===

=== Making Changes

. Create a new branch from `main`.
. Make your changes in small, focused commits.
. Follow the existing code style — the project uses **Prettier** and **ESLint**.
. Pre-commit hooks (Husky + lint-staged) will automatically lint and format staged files.
. Run the full check before pushing:

[source,bash]
----
pnpm lint
pnpm typecheck
pnpm test
pnpm build
----

All must pass with zero errors.

=== Commit Messages

Write clear, descriptive commit messages. Follow the https://www.conventionalcommits.org/[Conventional Commits] format:

----
<type>(<scope>): <description>

[optional body]

[optional footer]
----

Examples:

----
feat(audio): add silence detection threshold setting
fix(groq-client): handle empty audio blob gracefully
docs(readme): update architecture diagram
refactor(event-bus): simplify event type inference
----

== Code Style

This project enforces consistent style through tooling:

* **TypeScript** — strict mode enabled. All new code must be type-safe.
* **ESLint** — configured with `typescript-eslint` (type-aware rules). Run with `pnpm lint`.
* **Prettier** — handles formatting. Run with `pnpm format`.
* **No `any`** — avoid `any` types. Use proper type definitions in `src/types.ts` or near the module that owns them.
* **JSDoc** — every module has a file-level JSDoc comment describing its single responsibility. Maintain this convention.

=== Architecture Conventions

The application follows an **event-driven modular architecture**:

* All inter-module communication flows through the `EventBus` (`src/core/event-bus.ts`).
* Modules do **not** import each other directly. They emit and listen to events.
* `src/main.ts` is the **only** composition root — it wires everything together.
* Each module has a single responsibility (SRP).

When adding a new feature:

. Add type definitions to `src/types.ts` if they are shared.
. If the feature needs to communicate, define new event types and emit/listen via the EventBus.
. Keep the module self-contained. Do not reach into another module's internals.

== Submitting a Pull Request

. Push your branch to your fork.
. Open a Pull Request against the `main` branch of this repository.
. Fill in the PR template (if present) with:
** What changed and why.
** How to test it.
** Any screenshots or screen recordings for UI changes.
. Make sure `pnpm lint`, `pnpm typecheck`, and `pnpm test` pass on your branch.
. Keep PRs small and focused. Large PRs may be asked to be split.

=== PR Review Criteria

Reviewers will check for:

* Correctness — does the change do what it claims?
* Type safety — no `any`, no missing types.
* Architecture — does it respect the event-driven pattern?
* No regressions — existing functionality still works.
* No secrets — no API keys, tokens, or credentials in the diff.

== Reporting Issues

Use https://github.com/<your-username>/speech-to-text/issues[GitHub Issues] to report bugs or request features.

When filing a bug report, include:

. Steps to reproduce.
. Expected behavior.
. Actual behavior.
. Browser and OS.
. Console errors (if any).

== Security Vulnerabilities

**Do not file a public issue for security vulnerabilities.**

Report them privately via GitHub's **Security** tab → **Report a vulnerability**. See link:SECURITY.md[SECURITY.md] for the full policy.

== Running Tests

The project uses Vitest with jsdom for DOM APIs and MSW for HTTP mocking.

[source,bash]
----
# Run all tests once
pnpm test

# Watch mode
pnpm test:watch

# Coverage report (thresholds: 90% lines/functions/statements, 80% branches)
pnpm test:coverage
----

=== Adding a Pure-Module Test

Most utility and core modules are pure functions with no DOM or network
dependencies. Test them following the patterns in `tests/unit/`:

[source,typescript]
----
import { describe, it, expect } from 'vitest';
import { myFunction } from '../../src/utils/my-module';

describe('myFunction', () => {
  it('should do the expected thing', () => {
    expect(myFunction(input)).toBe(expected);
  });
});
----

For modules that use `localStorage` or `sessionStorage`, the polyfills in
`tests/helpers/setup.ts` are loaded automatically via `vitest.config.ts`.

For modules that make HTTP requests, use MSW handlers. See
`tests/helpers/msw-handlers.ts` for the Groq API mock setup and
`tests/unit/groq-client.test.ts` for usage examples.

== Adding a Tauri Command

See link:ARCHITECTURE.md#5-how-to-add-a-new-tauri-command[ARCHITECTURE.md §5]
for the full guide. Summary:

. Write the `#[tauri::command]` function in `src-tauri/src/commands/<area>.rs`.
. Register it in `src-tauri/src/lib.rs` via `generate_handler!`.
. Declare any needed permissions in `src-tauri/capabilities/default.json`.
. Add a method to the `Platform` interface and implement in both bridges.
. Write a unit test for the web-bridge fallback path.
